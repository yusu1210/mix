# Releasing Mix

The release workflow builds the same Rust Core and React UI that are tested
locally. It produces one notarized Mac App/DMG set for Apple Silicon and one
for Intel, plus signed Tauri updater archives, deterministic Cargo/npm SBOMs,
license evidence, `latest.json`, and checksums.

## Local verification

```bash
nvm use
sh scripts/quality-gate.sh
```

The quality gate and desktop build reject a Node version different from
`.nvmrc`. Workspace Rust bootstrap is pinned by rustup version, target and
SHA-256; changing any bootstrap binary is a reviewed supply-chain change.

On macOS, a local desktop build is ad-hoc signed:

```bash
cd apps/macos
npm run build:desktop
```

Local builds keep updater support disabled and do not contact a release
endpoint. `generate-third-party-licenses.sh` resolves the locked Rust graph
with `cargo-about`; the App bundles the resulting license page.
Local disposable Rust build output defaults to `/tmp/mix-target`. To keep a candidate separate
from another build or a running development App, set `CARGO_TARGET_DIR` to an
absolute directory. The Rust build, App bundle, DMG and updater tooling all
use that one directory; relative overrides fail before compilation so
post-processing cannot accidentally sign or package an artifact from another
target tree.
Set `MIX_LOCAL_OUTPUT_ROOT` to an absolute, non-symbolic-link directory when
the copied App and DMG must be staged without replacing a running
`.build/local-app/mix.app`; compilation still uses `CARGO_TARGET_DIR`.

Release builds use signed update metadata only to check whether a new version
exists. The shipped capability is check-only: download, install, and restart
permissions are absent. Users install the notarized DMG from the official
release page until a crash-safe macOS replacement transaction has separate
acceptance evidence.

## Protected release requirements

Create a protected GitHub Environment named `release` with required maintainer
approval. Store these values as environment secrets:

- `APPLE_CERTIFICATE`: base64-encoded Developer ID Application `.p12`.
- `APPLE_INSTALLER_CERTIFICATE`: base64-encoded Developer ID Installer `.p12`.
- `APPLE_CERTIFICATE_PASSWORD`, `APPLE_INSTALLER_CERTIFICATE_PASSWORD`, and
  `APPLE_KEYCHAIN_PASSWORD`.
- `APPLE_SIGNING_IDENTITY`, `APPLE_INSTALLER_SIGNING_IDENTITY`, `APPLE_ID`, the
  app-specific `APPLE_PASSWORD`, and `APPLE_TEAM_ID`.
- `TAURI_SIGNING_PRIVATE_KEY` and
  `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`.

Store the non-secret updater trust material as repository variables:

- `MIX_UPDATER_PUBLIC_KEY`: the public key embedded in the candidate App.
- `MIX_UPDATER_SIGNING_PUBLIC_KEY`: normally unset; the workflow falls back to
  the embedded key. Set it only for the bridge release described below.
- `MIX_UPDATER_ROTATION_BRIDGE_VERSION`: normally unset.

The workflow signs the final App before recreating the updater archive, then signs
and notarizes the DMG. It verifies the mounted App, architecture, deep
signature, Gatekeeper state, updater signature, SBOM artifact hash, and exact
release asset set before creating a draft. Secret values must never be added as
repository variables or workflow-dispatch inputs.

The Tauri updater `.app.tar.gz` containers are generated by the Rust release
tool with sorted UTF-8 paths, normalized modes, zero uid/gid/mtime, a fixed
gzip header, and bounded symlinks. Each release job creates the updater
container twice and requires byte equality. CLI delivery uses a macOS Installer
package so the executable and Local Web UI remain one versioned artifact while
becoming directly available on `PATH`. Signed packages and DMGs are not
expected to be byte-reproducible: secure timestamps, notarization tickets,
package metadata, and disk-image identifiers
intentionally vary. Final installers are bound by SHA-256, code signatures,
notarization, SBOMs, and GitHub provenance.

The Mac App, CLI, and Local Web read one private per-user credential directory.
Release signing proves artifact origin but is not coupled to credential access.
Clean-machine acceptance verifies that credentials created by either surface
are immediately available to the others without password prompts.

The macOS CLI release payload is
`mix_<version>_cli_<architecture>.pkg`. Its signed and notarized Installer
payload keeps `mix-cli.app` under `/Library/Application Support/Mix`, links
`/usr/local/bin/mix`, refuses to overwrite a foreign command, and includes the
single production React build under `Contents/Resources/ui`. It also installs
an ownership-checking `uninstall-cli` helper beside the bundle; uninstall must
fail closed for foreign paths and preserve Mix/native client data. A raw
executable is not a valid release payload. `mix web` must open that packaged UI
without `--ui` in clean-machine acceptance.

The draft is not public. Complete the bilingual acceptance template against
the exact draft assets on clean Apple Silicon and Intel machines. The required
manual gates include real Codex OAuth/API-key/provider switching, native
history continuity, Claude authentication/resume, update interruption and
rollback, accessibility, privacy, and uninstall. Only the protected
`Publish accepted release` workflow may promote the draft.

The completed acceptance file ends with the template's machine-readable sealed
decision. Commit it to the same repository and use the immutable raw URL for
that exact commit; branch, tag, HTML, redirecting, query-string, and
cross-repository references are rejected. Before publication, the protected
workflow parses the commit and path, checks the size, and downloads the exact
file through GitHub's authenticated [repository contents API](https://docs.github.com/en/rest/repos/contents)
using its raw media type. `mix-release` then verifies the supplied file digest,
exact repository/tag/draft URL, current `SHA256SUMS` digest,
release-manager decision, UTC review records, all eight evidence-bearing gates,
and the matching protected-workflow confirmations. It then emits acceptance
schema 3, binding those values to every payload hash, and re-verifies the exact
accepted asset set before the draft can become public.

## Release runbook

1. Update the version in the workspace `Cargo.toml`,
   `apps/macos/package.json`, and `apps/macos/src-tauri/tauri.conf.json`. Run
   `cargo run --locked --package mix-release -- meta check`.
2. Update release notes and compatibility evidence. Store raw compatibility
   output outside the public repository and run

   ```sh
   evidence_dir="${MIX_RELEASE_EVIDENCE_DIR:?set an absolute private evidence directory}"
   mkdir -p "$evidence_dir"

   cargo run --locked --package mix-release -- compatibility codex-provider-route \
     --codex /Applications/ChatGPT.app/Contents/Resources/codex \
     --output "$evidence_dir/client-compat-codex-provider.json"

   cargo run --locked --package mix-release -- compatibility claude-config-dir \
     --claude /absolute/path/to/claude \
     --output "$evidence_dir/client-compat-claude-config-dir.json"
   ```

   These disposable probes must pass for the exact client builds in the release
   matrix. The Codex probe binds a loopback-only fake Provider and a generated
   synthetic credential. The Claude probe uses separate temporary HOME and
   `CLAUDE_CONFIG_DIR` roots with authentication environment variables removed.
   Neither records credential values or replaces the real account/session
   continuity gates. Raw logs, screenshots, and local readiness reports stay
   outside Git; only the final sanitized acceptance record is committed.
   Then run `sh scripts/quality-gate.sh`,
   `cargo audit --file Cargo.lock`, and
   `npm audit --prefix apps/macos --audit-level=high` from a clean checkout.
3. Create and push the reviewed `vX.Y.Z` tag. Approve the protected build. The
   macOS release workflow must finish both native architecture jobs and create
   one draft release; do not publish from the GitHub Release UI.
4. Download only that draft's assets. Verify `SHA256SUMS`, signatures,
   notarization tickets, SBOMs, and the exact asset inventory before running the
   full bilingual acceptance template on clean Apple Silicon and native Intel
   systems.
5. Complete the sealed decision, verify it with `readiness evidence-verify`,
   compute its digest with `readiness evidence-hash`, and commit the unchanged
   file to the same repository. Use the raw URL containing that exact commit
   SHA; a branch or tag name is not accepted.
6. Dispatch **Publish accepted release** with the exact tag, raw evidence URL,
   digest, and all eight confirmations. The protected environment reviewer
   must compare the inputs with the sealed evidence before approving.
7. Confirm the release is public, `releases/latest/download/latest.json`
   resolves to the new two-architecture manifest, every expected asset is
   present, and the preceding production App performs one final read-only
   update check. Archive the acceptance links with the release record.

Any failure leaves the release as a draft. Do not edit a sealed evidence file,
reuse evidence from another candidate, or replace a published tag. A material
code, signing, packaging, or acceptance change requires a new candidate and
version.

## Updater key lifecycle

Generate and back up the updater private key offline. Keep its password and
backup in separately controlled locations. The App only checks signed metadata
and directs users to the official notarized DMG; it has no download, install,
or restart capability.

For a planned key rotation while the old private key is still trusted, build
one bridge release with the new public key in `MIX_UPDATER_PUBLIC_KEY`, keep
signing with the old private key, set `MIX_UPDATER_SIGNING_PUBLIC_KEY` to the old
public key, and set `MIX_UPDATER_ROTATION_BRIDGE_VERSION` to the exact bridge
SemVer. After that release is accepted, switch the signing secret to the new
private key and clear both rotation variables. Clients that skip the bridge
must update by manually verified notarized DMG.

If the old private key may be compromised, do not ship a bridge signed by it.
Pause update announcements, publish a security notice, rotate the key, and
require a manually verified notarized DMG. Losing the only private key has the
same manual-recovery consequence.

## Supply-chain rules

Cargo and npm dependencies must resolve to reviewed public sources. CI, tagged
release preflight, and final draft publication rerun pinned `cargo-audit` and
`npm audit` checks against the committed lockfiles. Release SBOMs are
deterministic and bind their root hash to the exact DMG. Secrets
must remain in GitHub secret storage or offline key material and must never be
written into artifacts, logs, command arguments, or repository files.

RustSec maintenance and unsoundness warnings are reviewed explicitly; they are
not hidden with blanket ignore rules. In the current lockfile, the GTK3,
`glib`, and `proc-macro-error` warnings do not enter either macOS target graph.
Five unmaintained `unic-*` crates do enter both macOS graphs through Tauri's
`tauri-utils -> urlpattern` chain; they have no known vulnerability, but remain
an upstream maintenance risk. Do not add a local fork merely to silence that
warning. Re-evaluate the exact target graph on every Tauri or lockfile update,
and remove the chain as soon as the maintained upstream dependency permits it.
Any known exploitable vulnerability in a shipped target blocks the release.
